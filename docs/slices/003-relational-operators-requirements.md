# Slice 003: Relational Operators Requirements Analysis

Status: Draft 0.1

Last updated: 2026-06-15

Related PRD: [docs/enact-prd.md](/home/tprover/2606_enact_auto/docs/enact-prd.md)

Prerequisite slice: [docs/slices/002-comparison-boolean-conditional-requirements.md](/home/tprover/2606_enact_auto/docs/slices/002-comparison-boolean-conditional-requirements.md)

## 1. Slice Goal

This slice completes the small primitive comparison family started in Slice 002:

- inequality using `!=`
- integer ordering using `<`, `>`, `<=`, and `>=`
- precedence compatibility with arithmetic, boolean logic, and conditionals
- stable type errors for unsupported relational operands

The purpose is to finish the non-identifier comparison core before introducing environments, assignment, or functions.

## 2. Source Basis

The ENACT reference material records the historical comparison operator family as:

- `=`
- `<>`
- `<`
- `>`
- `<=`
- `>=`

The project-default syntax already modernized historical equality from `=` to `==` in Slice 002. This slice also modernizes historical inequality from `<>` to `!=`, matching the PRD's project-default relational syntax.

## 3. In Scope

This slice includes:

- lexical recognition of `!=`, `<`, `>`, `<=`, and `>=`
- parser support for one relational operator between two additive expressions
- evaluation of integer ordering comparisons
- evaluation of same-kind inequality using `!=`
- stable type errors for invalid operands
- regression tests for precedence, boundary values, malformed relational expressions, and type misuse

## 4. Out Of Scope

This slice explicitly excludes:

- chained comparisons such as `1<2<3.`
- historical equality syntax `=`
- historical inequality syntax `<>`
- identifiers and variables
- assignment `:=`
- sequencing `;`
- functions, lambdas, `where`, `fix`, `load`, or `loop`
- strings, atoms, lists, objects, classes, sets, and bags
- ordering comparisons over non-integer values

These exclusions keep the slice focused on primitive comparisons only.

## 5. User-Facing Behavior

Representative accepted examples:

- `1!=2.` => `true`
- `1!=1.` => `false`
- `true!=false.` => `true`
- `1<2.` => `true`
- `2<1.` => `false`
- `2<=2.` => `true`
- `3>2.` => `true`
- `3>=4.` => `false`
- `1+2<4.` => `true`
- `not 1<2.` => `false`
- `1 if 2>=2 else 3.` => `1`

Every accepted input remains a single expression followed by `.`.

## 6. Lexical Requirements

The lexer shall recognize:

- `!=` as inequality
- `<` as less-than
- `>` as greater-than
- `<=` as less-than-or-equal
- `>=` as greater-than-or-equal

The lexer shall ensure:

- two-character operators are matched before their one-character prefixes
- all relational operators set operand expectation to true after emission
- existing bare `=` behavior remains unchanged: it is rejected with `ENACT_ERR_LEX_BARE_EQUALS`

## 7. Syntax Requirements

The parser shall accept expressions generated by this conceptual comparison subset:

```text
equality           ::= additive
                     | additive comparison_operator additive
comparison_operator ::= "=="
                      | "!="
                      | "<"
                      | ">"
                      | "<="
                      | ">="
```

Implementation may rename `equality` to a broader nonterminal such as `comparison`.

The parser shall preserve:

- arithmetic precedence above comparison
- `not`, `and`, `or`, and conditional precedence below comparison
- non-associative comparison behavior

Therefore:

- `1+2<4.` parses as `(1+2)<4`
- `not 1<2.` parses as `not (1<2)`
- `1<2<3.` is rejected

## 8. Semantic Requirements

The evaluator shall:

- evaluate `<`, `>`, `<=`, and `>=` over integer operands only
- return boolean results from all relational operators
- evaluate `!=` over operands with matching runtime kinds
- allow `!=` for integers and booleans in this slice
- reject cross-kind inequality such as `true!=1.`
- reject ordering comparisons involving booleans such as `true<false.` or `1<true.`
- preserve Slice 002 short-circuit and conditional laziness

The evaluator shall not:

- coerce integers to booleans
- coerce booleans to integers
- silently treat cross-kind inequality as `true`
- define ordering over booleans

## 9. Error Requirements

The implementation shall detect and report, at minimum:

- missing right operand for each relational operator
- leading relational operator such as `<1.`
- chained comparison such as `1<2<3.`
- cross-type inequality such as `true!=1.`
- non-integer ordering such as `true<false.`
- bare `=`

Existing diagnostic codes are sufficient:

- `ENACT_ERR_PARSE_UNEXPECTED_TOKEN` for malformed relational syntax
- `ENACT_ERR_TYPE_EQUALITY_MISMATCH` for cross-kind `!=`
- `ENACT_ERR_TYPE_EXPECTED_INT` for non-integer ordering operands
- `ENACT_ERR_LEX_BARE_EQUALS` for bare `=`

## 10. Boundary Analysis Requirements

The regression suite for this slice shall include at least:

- `0<1.`
- `1<0.`
- `1<=1.`
- `2147483647>=2147483647.`
- `-2147483648<=-2147483648.`
- `-1<0.`
- `0>-1.`
- `1!=2.`
- `1!=1.`
- `true!=false.`
- `true!=true.`
- `1+2<4.`
- `not 1<2.`
- `1 if 2>=2 else 3.`

## 11. Robustness Requirements

The regression suite for this slice shall include malformed or risky cases such as:

- `<.`
- `<1.`
- `1<.`
- `1<2<3.`
- `1!=.`
- `true!=1.`
- `true<false.`
- `1<true.`
- `1<=.`
- `1>=.`
- bare `=`

## 12. Acceptance Criteria

This slice is accepted when:

- all five deferred comparison operators are tokenized
- parser precedence remains compatible with Slice 002
- chained comparisons remain rejected
- ordering operators are integer-only
- `!=` behaves as same-kind inequality
- all new behavior is covered by regression tests
- existing Slice 001 and Slice 002 tests remain green
