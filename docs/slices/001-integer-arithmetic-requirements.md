# Slice 001: Integer Arithmetic Requirements Analysis

Status: Draft 0.1

Last updated: 2026-06-14

Related PRD: [docs/enact-prd.md](/home/tprover/2606_enact_auto/docs/enact-prd.md)

## 1. Slice Goal

This slice defines the first executable ENACT core feature:

- integer literals
- arithmetic expressions over integers
- the four arithmetic operators `+`, `-`, `*`, `/`
- parenthesized grouping
- correct precedence and associativity

The purpose of this slice is to create the smallest useful evaluator core on which later expression forms can safely build.

## 2. Source Basis

This slice is grounded in the ENACT reference manual content visible in [260614_enact_manual.pdf](/home/tprover/2606_enact_auto/260614_enact_manual.pdf), especially the appendix pages showing:

- expression evaluation and operator precedence
- integer lexical rules
- arithmetic operator descriptions
- the example `1+2*3+4*5+6.` evaluating to `33`

The following facts are directly supported by the manual:

- ENACT is expression-based.
- Arithmetic operators include `+`, `-`, `*`, `/`, and `mod`.
- Arithmetic operators compute integer values using 32-bit arithmetic.
- There is no unary minus.
- Negative numbers are written using `~`, for example `~99`.
- `*` and `/` bind more tightly than `+` and `-`.
- Binary operators at the same precedence level associate to the left.
- Expressions are terminated by `.`.

For this project, we intentionally modernize that historical rule:

- project-default syntax uses unary `-` instead of historical `~`
- lexical analysis and parsing must explicitly distinguish `UNARY_MINUS` from binary subtraction
- the user-facing language should therefore accept standard negative integer notation such as `-99`

## 3. In Scope

This slice includes:

- decimal integer literals
- negative integer literals using unary `-`
- unary minus over integer arithmetic expressions
- binary arithmetic operators `+`, `-`, `*`, `/`
- parentheses for grouping
- expression termination using `.`
- integer result printing
- parser and evaluator support for precedence and left associativity
- regression tests for normal, boundary, and malformed arithmetic input

## 4. Out Of Scope

This slice explicitly excludes:

- `mod`
- comparison operators
- logical operators
- variables and identifiers in arithmetic expressions
- function definition and application
- assignment
- strings, atoms, lists, sets, classes, objects, and methods
- local definitions, conditionals, `fix`, and `load`
- overflow recovery or bignum support

These excluded items may depend on this slice later, but this slice should not wait for them.

## 5. User-Facing Behavior

The system should allow a user to enter arithmetic expressions in ENACT syntax and receive an integer result.

Representative examples:

- `1+2.` => `3`
- `1+2*3.` => `7`
- `(1+2)*3.` => `9`
- `1+2*3+4*5+6.` => `33`
- `-4+10.` => `6`
- `1*-2.` => `-2`
- `-(1+2)*3.` => `-9`
- `8/2.` => `4`

At this stage, every accepted input is a single arithmetic expression followed by `.`.

## 6. Lexical Requirements

The lexer shall recognize:

- unsigned decimal integer literals consisting of one or more digits
- operators `+`, `-`, `*`, `/`
- minus signs in unary position as `UNARY_MINUS`
- minus signs in infix position as binary subtraction
- left and right parentheses
- terminating `.`
- whitespace between tokens
- line comments beginning with `%` and extending to newline

The lexer shall reject or surface errors for:

- malformed integer forms
- malformed uses of unary minus such as `-.`
- illegal characters in this slice

## 7. Syntax Requirements

The parser shall accept expressions generated by the following conceptual grammar subset:

```text
input              ::= expr "."
expr               ::= additive
additive           ::= multiplicative
                     | additive "+" multiplicative
                     | additive "-" multiplicative
multiplicative     ::= unary
                     | multiplicative "*" unary
                     | multiplicative "/" unary
unary              ::= primary
                     | UNARY_MINUS unary
primary            ::= integer
                     | "(" expr ")"
integer            ::= digits
```

This grammar is conceptual guidance for the slice. Final `bison` structure may differ if needed, but it must preserve the same behavior.

## 8. Semantic Requirements

The evaluator shall:

- evaluate integer literals to integer runtime values
- evaluate unary minus over integer operands
- apply `+`, `-`, `*`, and `/` to integer operands only
- honor operator precedence with `*` and `/` binding more tightly than `+` and `-`
- honor unary minus precedence above multiplicative operators
- evaluate same-precedence binary arithmetic operators left-to-right
- evaluate parentheses before surrounding operators
- print the resulting integer value in decimal form

The evaluator shall not:

- silently coerce non-integer values
- accept incomplete expressions

## 9. Numeric Semantics

The manual states that arithmetic computes integer values using 32-bit arithmetic. For this slice, the following requirement is therefore adopted:

- the runtime integer domain shall be modeled as signed 32-bit integer behavior, or as an internal representation that is externally compatible with signed 32-bit ENACT behavior

One semantic detail remains open for design:

- exact division semantics for negative operands and overflow edge behavior are not fully evidenced by the currently reviewed manual pages

This means design must explicitly choose and document:

- division behavior for negative numbers
- overflow behavior for addition, subtraction, multiplication, and division
- minimum-value negation edge behavior for `-2147483648` if supported

## 10. Error Requirements

The implementation shall detect and report, at minimum:

- missing terminating `.`
- missing operand, such as `1+.` or `*2.`
- mismatched parentheses
- malformed unary minus usage, such as `-.`
- division by zero
- unexpected trailing tokens after a valid expression

Error messages do not need to be polished in this slice, but they must be stable enough for regression testing.

## 11. Boundary Analysis Requirements

The regression suite for this slice shall include at least:

- `0.`
- `1.`
- `-1.`
- `2147483647.`
- `-2147483648.` if supported by the chosen lexer and integer representation
- `0+0.`
- `1-1.`
- `1*0.`
- `0/1.`
- `1*-1.`
- `-(1).`
- nested parentheses such as `((((1)))).`
- long left-associated chains such as `1-2-3-4.`
- mixed precedence such as `1+2*3-4/2.`

## 12. Robustness Requirements

The regression suite for this slice shall include malformed or risky cases such as:

- empty input
- `1`
- `.`
- `+1.`
- `-.`
- `1*-.`
- `1+-.`
- `1/.`
- `1/(2-2).`
- `(1+2.`
- `1+2).`
- `1++2.`
- `1 2.`
- `% comment only`

## 13. Acceptance Criteria

This slice is ready to move from requirements analysis to design when the following are accepted:

- the slice is limited to integer arithmetic only
- negative values are written with unary `-`
- unary minus is a supported part of this slice, not a deferred feature
- `+`, `-`, `*`, and `/` are the only arithmetic operators in this slice
- precedence and left associativity rules are fixed
- `mod` is intentionally deferred
- 32-bit compatibility is a requirement, even if exact internal representation is still a design choice
- parser and evaluator error handling are considered part of the slice, not optional extras

## 14. Design Inputs For Next Step

The next design step must decide:

- how integer tokens are represented in the lexer
- the exact lexical-context rule for emitting `UNARY_MINUS`
- the internal runtime integer type
- overflow handling policy
- division semantics policy
- the exact shape of AST nodes for arithmetic expressions
- the minimal test harness structure for parser and evaluator regression tests

## 15. Recommended First Regression Cases

The following cases should be the first golden tests once implementation begins:

- `1+2.` => `3`
- `1+2*3.` => `7`
- `(1+2)*3.` => `9`
- `1+2*3+4*5+6.` => `33`
- `8/2.` => `4`
- `-4+10.` => `6`
- `-(1+2).` => `-3`
- `1-2-3.` => `-4` if printed in project form compatible with integer output

The following cases should be the first negative tests:

- `-.`
- `1+.`
- `(1+2.`
- `1/0.`
- `1`

## 16. Review Notes

This slice is intentionally smaller than the full arithmetic capability documented by the manual. The manual includes `mod`, but this slice excludes it so that:

- precedence implementation can be verified with fewer operators
- integer runtime and divide-by-zero handling can be stabilized first
- regression infrastructure can be established before the grammar expands

The main semantic risk in this slice is not parsing but arithmetic compatibility:

- 32-bit behavior
- division behavior
- overflow behavior

These should be settled explicitly in the design phase and then frozen in tests.
