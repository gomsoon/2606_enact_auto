# Slice 002: Comparison, Boolean, and Conditional Core Requirements Analysis

Status: Draft 0.1

Last updated: 2026-06-15

Related PRD: [docs/enact-prd.md](/home/tprover/2606_enact_auto/docs/enact-prd.md)

Prerequisite slice: [docs/slices/001-integer-arithmetic-requirements.md](/home/tprover/2606_enact_auto/docs/slices/001-integer-arithmetic-requirements.md)

## 1. Slice Goal

This slice defines the next executable ENACT core feature after integer arithmetic:

- equality comparison using `==`
- boolean runtime values
- boolean operators `not`, `and`, `or`
- a small conditional expression core
- precedence between arithmetic, comparison, boolean logic, and conditionals

The purpose of this slice is to create the smallest useful decision-making core on top of Slice 001, without yet introducing identifiers, assignment, or broader control-flow syntax.

## 2. Source Basis

This slice is grounded in the ENACT reference manual summary captured in [docs/enact-prd.md](/home/tprover/2606_enact_auto/docs/enact-prd.md), especially the requirements and precedence notes stating that:

- comparison operators historically include `=`, `<>`, `<`, `>`, `<=`, `>=`
- logical expressions include `and`, `or`, and unary `not`
- conditional expressions involve `if`, `then`, and `else`
- comparison binds below arithmetic
- boolean logic binds below comparison
- conditional operators bind below boolean logic

For this project, we intentionally keep the second slice smaller than the full historical comparison and conditional family:

- project-default equality syntax uses `==` instead of historical `=`
- this slice includes only `==` from the comparison family
- project-default boolean literals are written as `true` and `false`
- this slice fixes one canonical conditional surface form: `true_expr if condition else false_expr`
- historical or alternate `then`-led conditional forms are intentionally deferred

This is consistent with the modernization strategy already adopted in Slice 001 for unary `-`.

## 3. In Scope

This slice includes:

- boolean literals `true` and `false`
- equality comparison using `==`
- boolean operators `not`, `and`, `or`
- parentheses around boolean and conditional expressions
- conditional expressions written as `true_expr if condition else false_expr`
- use of Slice 001 arithmetic expressions inside comparison operands, conditions, and branches
- stable parser and evaluator behavior for precedence, associativity, and lazy branch selection
- regression tests for normal, boundary, and malformed comparison and conditional input

## 4. Out Of Scope

This slice explicitly excludes:

- relational operators other than `==`, including `<`, `>`, `<=`, `>=`, `<>`
- historical equality syntax `=`
- historical or alternate conditional spellings involving `then`
- identifiers and variables
- assignment `:=`
- sequencing `;`
- `where`, `fix`, `load`, and `loop`
- function definition and application
- strings, atoms, lists, sets, classes, objects, and methods
- implicit truthiness or falsiness rules
- equality over future value categories such as strings, atoms, lists, objects, or sets

These excluded items may depend on this slice later, but this slice should not wait for them.

## 5. User-Facing Behavior

The system should allow a user to enter arithmetic-plus-boolean expressions in ENACT project-default syntax and receive either an integer result or a boolean result.

Representative examples:

- `true.` => `true`
- `false.` => `false`
- `1==1.` => `true`
- `1==2.` => `false`
- `1+2==3.` => `true`
- `not false.` => `true`
- `true and false.` => `false`
- `false or true.` => `true`
- `1 if true else 2.` => `1`
- `1 if 2==3 else 2.` => `2`
- `10 if true and not false else 20.` => `10`

At this stage, every accepted input is still a single expression followed by `.`.

## 6. Lexical Requirements

The lexer shall recognize:

- boolean literals `true` and `false`
- boolean operators `not`, `and`, `or`
- conditional keywords `if` and `else`
- equality operator `==`
- all Slice 001 arithmetic tokens, including integers, `+`, `-`, `*`, `/`, parentheses, `.`, whitespace, and `%` comments

The lexer shall ensure:

- `==` is emitted as one comparison token, not two separate `=` characters
- a single bare `=` is not accepted in the project-default syntax for this slice
- `if`, `else`, `and`, `or`, `not`, `true`, and `false` are not tokenized as ordinary identifiers inside this slice

The lexer shall reject or surface errors for:

- a bare `=`
- illegal characters in this slice
- malformed token boundaries that prevent `==` from being recognized as intended

## 7. Syntax Requirements

The parser shall accept expressions generated by the following conceptual grammar subset:

```text
input              ::= expr "."
expr               ::= conditional
conditional        ::= logical_or
                     | logical_or "if" logical_or "else" conditional
logical_or         ::= logical_and
                     | logical_or "or" logical_and
logical_and        ::= logical_not
                     | logical_and "and" logical_not
logical_not        ::= equality
                     | "not" logical_not
equality           ::= additive
                     | additive "==" additive
additive           ::= multiplicative
                     | additive "+" multiplicative
                     | additive "-" multiplicative
multiplicative     ::= unary
                     | multiplicative "*" unary
                     | multiplicative "/" unary
unary              ::= primary
                     | UNARY_MINUS unary
primary            ::= integer
                     | boolean
                     | "(" expr ")"
boolean            ::= "true"
                     | "false"
integer            ::= digits
```

This grammar is conceptual guidance for the slice. Final `bison` structure may differ if needed, but it must preserve the same behavior.

The following syntax constraints are intentionally fixed for this slice:

- `==` is non-associative in intended user behavior
- chained forms such as `1==2==3.` shall be rejected unless explicit parentheses make the grouping unambiguous
- `if ... else ...` is right-associative in intended user behavior
- arithmetic precedence from Slice 001 remains intact underneath comparison and boolean logic

## 8. Semantic Requirements

The evaluator shall:

- evaluate `true` and `false` to boolean runtime values
- evaluate `==` and return a boolean runtime value
- allow `==` over integer operands
- allow `==` over boolean operands
- allow Slice 001 arithmetic expressions to appear as operands of `==`
- evaluate `not`, `and`, and `or` over boolean operands only
- evaluate `true_expr if condition else false_expr` by evaluating the condition first
- return the selected branch result unchanged
- preserve Slice 001 arithmetic semantics when arithmetic subexpressions appear inside comparison or branch expressions

The evaluator shall also enforce:

- `and` evaluates left-to-right and short-circuits when the left operand is `false`
- `or` evaluates left-to-right and short-circuits when the left operand is `true`
- conditional evaluation does not evaluate the unselected branch

The evaluator shall not:

- silently coerce integers to booleans
- silently coerce booleans to integers
- silently coerce cross-type equality into `false`
- evaluate both sides of `and`, `or`, or conditional expressions when short-circuit rules say it should not

## 9. Boolean And Type Semantics

This slice introduces a dedicated boolean runtime domain.

The following requirements are adopted:

- boolean values print as lowercase `true` and `false`
- integer arithmetic remains integer-only
- boolean logic remains boolean-only
- conditions must be boolean-valued
- cross-type equality such as `true==1.` is a runtime type error in this slice

One deliberate simplification is allowed:

- the parser does not need to reject all type-invalid combinations statically

This means expressions such as `true+1.` may parse if that keeps the grammar simple, but they must fail during evaluation with stable diagnostics.

## 10. Error Requirements

The implementation shall detect and report, at minimum:

- missing terminating `.`
- missing right operand for `==`
- missing right operand for `and` or `or`
- malformed unary `not` usage such as `not.`
- malformed conditional forms such as `1 if true.` or `1 if else 2.`
- use of bare `=`
- non-boolean operand to `not`
- non-boolean operand to `and` or `or`
- non-boolean condition in `if ... else ...`
- cross-type equality such as `true==1.`
- arithmetic misuse of booleans such as `true+1.`

Error messages do not need to be polished in this slice, but they must be stable enough for regression testing.

## 11. Boundary Analysis Requirements

The regression suite for this slice shall include at least:

- `true.`
- `false.`
- `1==1.`
- `1==0.`
- `0==0.`
- `-1==-1.`
- `(1+2)==3.`
- `true==true.`
- `true==false.`
- `not true.`
- `not false.`
- `not not true.`
- `true and true.`
- `true and false.`
- `false or false.`
- `false or true.`
- `not false and true.`
- `false and 1/0==0.` to confirm short-circuit behavior
- `true or 1/0==0.` to confirm short-circuit behavior
- `1 if true else 2.`
- `1 if false else 2.`
- `1 if 1==1 else 2.`
- `1 if false else 2 if true else 3.` to confirm nested conditional association

## 12. Robustness Requirements

The regression suite for this slice shall include malformed or risky cases such as:

- empty input
- `true`
- `==.`
- `1==.`
- `1==2`
- `1==2==3.`
- `not.`
- `and true.`
- `true and.`
- `or false.`
- `false or.`
- `1 and true.`
- `1 or false.`
- `1 if true.`
- `1 if else 2.`
- `1 if 1 else 2.`
- `1 if true else.`
- `true==1.`
- `true+1.`
- `1+false.`
- bare `=`
- `% comment only`

## 13. Acceptance Criteria

This slice is ready to move from requirements analysis to design when the following are accepted:

- comparison is intentionally limited to `==`
- boolean literals are written as `true` and `false`
- boolean operators are limited to `not`, `and`, and `or`
- the canonical conditional surface form is `true_expr if condition else false_expr`
- historical `=` and `then`-led conditionals are intentionally deferred
- arithmetic remains stricter than comparison, comparison remains stricter than boolean logic, and conditional remains the loosest operator family in this slice
- short-circuit behavior for `and`, `or`, and conditional branch selection is part of the slice, not a later optimization
- type errors are part of the slice, not optional polish

## 14. Design Inputs For Next Step

The next design step must decide:

- the exact token names for `==`, `true`, `false`, `not`, `and`, `or`, `if`, and `else`
- the runtime value representation for booleans
- the exact AST node shapes for boolean literals, equality, logical operators, and conditional expressions
- the exact parser strategy for making `==` non-associative
- the exact parser strategy for right-associative nested conditionals
- the diagnostic codes for boolean type errors and conditional misuse
- whether the parser should admit type-invalid arithmetic-plus-boolean mixtures and defer them entirely to the evaluator

## 15. Recommended First Regression Cases

The following cases should be the first golden tests once implementation begins:

- `true.` => `true`
- `false.` => `false`
- `1==1.` => `true`
- `1==2.` => `false`
- `1+2==3.` => `true`
- `not false.` => `true`
- `true and false.` => `false`
- `false or true.` => `true`
- `1 if true else 2.` => `1`
- `1 if false else 2.` => `2`

The following cases should be the first negative tests:

- `1==.`
- `not.`
- `1 and true.`
- `1 if true.`
- `true==1.`
- `=`

## 16. Review Notes

This slice is intentionally smaller than the full comparison, logical, and conditional capability described in the PRD. The PRD includes a broader comparison family and mentions both `if` and `then`, but this slice excludes most of that so that:

- one comparison operator can be stabilized before the relational family expands
- one boolean runtime domain can be introduced before identifiers and environments arrive
- one conditional surface form can be frozen before broader control-flow syntax is added
- short-circuit and lazy-branch semantics can be regression-tested before side-effecting features appear

The main semantic risks in this slice are:

- precedence between arithmetic, equality, `not`, `and`, `or`, and conditional expressions
- non-associative `==` behavior
- short-circuit behavior
- boolean versus integer type discipline

These should be settled explicitly in the design phase and then frozen in tests.
